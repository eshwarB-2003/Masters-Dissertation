# Overview

This repository contains the practical work conducted for my MSc dissertation.

The objective of this study is to compare software architectures generated by Large Language Models (LLMs) with software architectures designed by human software architects.

The comparison is performed using published software architecture case studies. For each case study, an implementation-independent Software Requirements Specification (SRS) is extracted from the research paper and used as the sole input for AI-based architecture generation.

The AI-generated architecture is then compared with the original human-designed architecture using a structured software architecture evaluation framework.

---

# Research Aim

To compare AI-generated and human-designed software architectures derived from identical Software Requirements Specifications (SRS) using a consistent architecture evaluation framework.

---

# Research Questions

### RQ1

How do AI-generated software architectures compare with published human-designed software architectures when derived from the same Software Requirements Specification (SRS)?

### RQ2

To what extent do AI-generated software architectures satisfy the functional and architecturally significant quality requirements derived from the Software Requirements Specification?

### RQ3

What recurring patterns, strengths, and limitations emerge across multiple case studies when comparing AI-generated and published human-designed software architectures?

# Practical Workflow

## Phase 1 — Case Study Selection

Peer-reviewed software architecture papers are selected based on:

- Complete architecture description
- Architecture diagrams
- Sufficient system requirements
- Component descriptions
- Ability to derive an implementation-independent SRS

---

## Phase 2 — SRS Extraction

A Software Requirements Specification (SRS) is extracted from each paper using a standardized extraction prompt based on IEEE 29148.

The extraction process:

- preserves only requirements
- removes architecture
- removes implementation
- removes technologies
- removes algorithms
- removes design decisions

The extracted SRS becomes the only input provided to ChatGPT.

---

## Phase 3 — AI Architecture Generation

Each SRS is provided to ChatGPT using the same prompt.

The AI generates:

- Architecture Style
- Components
- Responsibilities
- Component Relationships
- Architecture Diagram
- Architecture Description

The AI is not given access to the original paper or architecture.

---

## Phase 4 — Human Architecture Extraction

The original software architecture is extracted from the research paper.

The following information is recorded:

- Architecture Style
- Components
- Responsibilities
- Architecture Diagram
- Architectural Description

---

## Phase 5 — Requirements-to-Architecture Traceability

Each requirement contained within the SRS is mapped to the corresponding architectural components.

The objective is to determine whether the architecture satisfies the documented requirements.

Coverage levels:

- Fully Covered
- Partially Covered
- Not Covered

---

## Phase 6 — Architecture Evaluation

Both architectures are evaluated independently using the same framework.

| Evaluation Metric | Source |
|-------------------|-----------------------------|
| Functional Coverage | ISO/IEC 25010 |
| Modularity | Bass, Clements & Kazman |
| Maintainability | ISO/IEC 25010 |
| Scalability | Bass, Clements & Kazman |
| Interoperability | ISO/IEC 25010 |
| Security | ISO/IEC 25010 |
| Requirements-to-Architecture Traceability | ISO/IEC/IEEE 29148 & ISO/IEC/IEEE 42010 |

Each metric is evaluated using a predefined 1–5 rubric.

Scores are assigned only where architectural evidence exists.

---

## Phase 7 — Architecture Comparison

Each case study compares:

- Architecture Style
- Component Structure
- Functional Coverage
- Modularity
- Maintainability
- Scalability
- Security
- Interoperability
- Requirements Traceability

---

## Phase 8 — Cross-Case Analysis

After all case studies have been evaluated, the findings are analysed collectively.

The analysis identifies:

- recurring strengths
- recurring weaknesses
- recurring architectural decisions
- recurring omissions
- quality attribute trends
- similarities between AI and human architectures
- differences between AI and human architectures

# Evaluation Framework

The evaluation framework is derived from internationally recognised software engineering standards and software architecture literature.

Primary references include:

- ISO/IEC 25010
- ISO/IEC/IEEE 29148
- ISO/IEC/IEEE 42010
- Software Architecture in Practice (Bass, Clements & Kazman)

---

# Research Contribution

This research contributes:

- A reproducible methodology for comparing AI-generated and human-designed software architectures.
- A standardized process for deriving Software Requirements Specifications from published software architecture papers.
- An evidence-based architecture evaluation framework.
- A comparative empirical study of AI-generated and human-designed software architectures across multiple software domains.

---

# Reproducibility

To ensure methodological consistency:

- The same SRS extraction prompt is used for every case study.
- The same AI prompt is used for architecture generation.
- The same evaluation framework is applied to all architectures.
- All evaluations are evidence-based.
- No assumptions are made beyond the information explicitly documented in the source material.

This repository contains all prompts, extracted artefacts, evaluation templates, and comparison results required to reproduce the study.
